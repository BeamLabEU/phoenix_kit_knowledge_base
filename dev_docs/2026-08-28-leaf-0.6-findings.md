# Leaf 0.6.0: what it brings us

Leaf 0.6.0 landed 2026-08-28, alongside `phoenix_kit` 2.13.13. Two of its
features are things this module had on its roadmap. One is now done; the other
is a real piece of work, and this records what it would take before anyone
starts it.

## The version pair moves together

`phoenix_kit` vendors the jsDelivr pin for Leaf's JS — Leaf is not bundled by
this module or by core's build, it is fetched at runtime. 2.13.10 pins
`leaf@v0.5.1`; **2.13.13 pins `leaf@v0.6.0`**. So the Elixir dependency and the
browser bundle are two halves of one contract and cannot be upgraded
separately. Leaf 0.6 warns in the console when the two disagree, which is new
and worth knowing: before, a stale bundle was silent.

Our declared `~> 0.5` already admits 0.6.0 — a two-component `~>` allows up to
the next major — so no constraint change was needed, only a lock update.

## Done: `[[wiki-links]]` in the editor

This was "Leaf Stage 0" in the founding goals and the next visible win in the
2026-08-26 review. Turned on with `wiki_links={%{resolve: true}}`.

The protocol is a round trip, because only the host knows which notes exist:

    {:leaf_resolve_links, %{editor_id:, targets: [...], seq:}}
    send_update(Leaf, id:, action: :link_targets, seq:, targets: %{...})
    {:leaf_link_clicked, %{editor_id:, target:, heading:, href:}}

Three things about it that mattered:

- **The targets arrive bare.** Leaf strips the alias and the heading anchor into
  separate attributes, so what we get is what `Markdown.normalize_title/1`
  wants. No parsing on our side.
- **The answer has to use the same resolver as the index.** `Links.resolve/3`
  with the open note's folder, or a link would render as pointing at one note
  while the backlinks panel named another. That is why resolution is answered
  only for the open note's editor: the same-folder tie-break is relative to the
  *linking* note, so a request from an editor that is no longer open would be
  resolved against the wrong folder.
- **Leaf never navigates**, deliberately — it reports a click and leaves the
  destination to us. We re-resolve the target rather than trusting the `href`
  that came back, on the same principle as `find_trash_entry/2`: a page that may
  be stale must not get to name the destination.

Ambiguity became visible for free. A bare title several notes answer to still
resolves, and the tooltip now says how many share it and which one won — the
review's point that a guessed link looks exactly like a correct one.

## Not done: live editing

`Leaf.Collab.join/2` is genuinely one call, and `Leaf.Collab.Store` is a clean
seam. It is still a substantial change here, for four reasons.

**It is not a CRDT.** Operations are rebased against each other and one that
cannot be placed is refused and resynced rather than applied at an offset. Two
people editing the same characters at the same instant converge, but somebody's
keystroke loses. (Note for a reader: `Leaf.Collab.Room`'s moduledoc still
describes itself as a testbed where mismatches are "recorded rather than
resolved". That text is stale — `rebase_over/2` and the refusal path are right
there in the same file.)

**A collaborating LiveView stops receiving `{:leaf_changed, …}`.** The hook
consumes it. So `save_decision/3`, `save_content/3`, the status pill and the
conflict banner — including the day-one fix for a debounced edit arriving after
a note switch — are all replaced by `Leaf.Collab.Store`, not extended by it.

**`Leaf.Collab.Store.File` is not usable as-is.** It is the reference
implementation and it fits the *storage* model exactly — hash recorded on read,
checked before write, `{:error, :conflict}` rather than an overwrite, which is
our stale guard by another name. But it writes the file and indexes nothing, so
Postgres would go stale on every collaborative edit: title, front matter, tags,
the link graph, the search vector. We want our own store calling
`Notes.update_content/4`, which already writes-to-disk-then-indexes and has the
guard, mapping our `{:error, :stale}` to Leaf's `{:error, :conflict}`. That
keeps both invariants and reuses what is already tested.

**Rooms are the host's to run, and ours would have to switch.** One process per
note, started on demand, supervised, stopped when the last person leaves —
infrastructure this module does not have yet. Worse, `join/2` is documented in
`mount` and hard-codes `attach_hook(:leaf_collab, …)`, and LiveView **raises**
on a duplicate hook id. `VaultLive` deliberately never remounts when you switch
notes — that is what keeps the sidebar alive — but switching note means
switching room. There is no `Leaf.Collab.leave/1`. We can `detach_hook` and
unsubscribe ourselves, but the room tracks sessions by pid, so the person would
linger as a ghost cursor in the note they just left for as long as the tab
stays open.

That last one is the design question to settle first, and it may be worth
asking upstream for a `leave/1` rather than working around it.

## Superseded

`2026-08-25-leaf-collaboration-spec.md` proposed adopting `y_ex` and keeping a
CRDT in Postgres, flushed to the file on a timer. Leaf did not take the CRDT
route, so the `y_ex` half is moot — but the storage half is exactly what
`Leaf.Collab.Store` implements, including the flush timer. Awareness also
supersedes the "presence and a soft lock" step, which existed only because
real co-editing was out of reach.
